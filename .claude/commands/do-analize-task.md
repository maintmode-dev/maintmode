# Do Analize Task

Анализ и планирование задач из директории `.agent_tasks`. Эта команда помогает декомпозировать задачи, оценивать время выполнения и создавать детальные планы.

## Роль агента

При анализе задач агент действует как:
- **Senior системный аналитик с 7-летним опытом** - декомпозиция требований, оценка времени, выявление рисков
- **Senior-разработчик с 5-летним опытом работы** на технологическом стеке проекта (см. `.agent/quick_load.toon`):
  - Backend: Go 1.25.0+, Echo, PostgreSQL, jet, sqlx, goose
  - Deployment: Docker

## Структура задач

Задачи организованы в директории `.agent_tasks/`:

```
.agent_tasks/
├── todo/              # Задачи к выполнению
│   └── task-name/     # Директория задачи
│       ├── task.md    # Описание задачи (после согласования плана)
│       ├── task.draft.md  # План задачи (до согласования, затем удаляется)
│       ├── materials/ # Дополнительные материалы (опционально)
│       ├── 1-subtask-setup/      # Подзадача 1 (опционально)
│       │   ├── task.md
│       │   └── materials/
│       ├── 2-subtask-implementation/  # Подзадача 2 (опционально)
│       │   └── task.md
│       └── 3-subtask-testing/    # Подзадача 3 (опционально)
│           └── task.md
├── done/              # Завершенные задачи (НЕ анализировать)
└── backlog/           # Задачи в резерве
```

### Формат именования

- **Директории задач**: `<task-name>` (например, `do-task`, `add-logging`, `fix-auth`)
- **Директории подзадач**: `<n>-subtask-<name>` где `n` - порядковый номер (например, `1-subtask-setup`, `2-subtask-implementation`)
- **Файлы задач**:
  - `task.md` - финальное описание задачи (после согласования)
  - `task.draft.md` - черновик плана (создается агентом, согласуется с пользователем, затем удаляется)

### Содержимое task.md

Каждый файл `task.md` может содержать:
- Описание того, что нужно сделать
- Критерии приемки
- Заметки по реализации
- Связанные файлы/компоненты
- Метаданные (зависимости, предусловия) - если требуется

## Workflow анализа задачи

### Шаг 1: Подготовка (ВСЕГДА в начале)

1. **Загрузить контекст проекта** используя команду `/load-context`
2. **Проверить текущую ветку**: `git branch --show-current`
   - Если на main/master - создать feature branch
   - Если на feature branch - продолжить работу
3. **Найти задачу**:
   - Если пользователь указал имя - использовать эту задачу
   - Если не указал - показать список доступных задач

### Шаг 2: Анализ структуры задачи

1. **Проверить наличие подзадач**:
   ```bash
   find .agent_tasks/todo/task-name -type d -name "*-subtask-*" | sort
   ```
2. **Прочитать task.md** и все дополнительные материалы в директории задачи
3. **Определить текущее состояние**:
   - Есть ли уже `task.draft.md` (план уже создан, нужно только согласование)
   - Есть ли только краткое описание в `task.md` (нужен полный анализ)
   - Есть ли уже созданные подзадачи

### Шаг 3: Создание плана выполнения

1. **Создать task.draft.md** в директории задачи на русском языке
2. **Структура task.draft.md**:
   ```markdown
   # Название задачи

   ## Анализ текущего состояния
   - Что уже есть в проекте
   - Что нужно изменить/добавить

   ## Цель задачи
   - Четкое описание конечного результата

   ## План выполнения

   ### Этап 1: Название (X часов)
   **Файлы**: путь/к/файлу.go
   **Изменения**:
   1. Конкретное действие 1
   2. Конкретное действие 2

   ### Этап 2: Название (Y часов)
   ...

   ## Оценка времени выполнения
   **Общее время**: X человеко-часов
   **Разбивка**:
   - Этап 1: X часов
   - Этап 2: Y часов

   **Вывод**: Требуется/не требуется разбиение на подзадачи

   ## Необходимые ресурсы
   - Дополнительная информация/материалы

   ## Критерии готовности
   - [ ] Критерий 1
   - [ ] Критерий 2

   ## Риски и вопросы
   - Что может пойти не так
   - Что нужно уточнить у пользователя
   ```

3. **Оценить время выполнения**:
   - Оценить каждый этап в человеко-часах
   - Суммировать общее время
   - **Если общее время > 3-5 часов** → создать подзадачи

4. **Создать подзадачи** (если требуется):
   - Разбить задачу на подзадачи длительностью не более 3-5 часов каждая
   - Создать директории `1-subtask-<name>`, `2-subtask-<name>`, и т.д.
   - В каждой директории создать `task.md` с детальным описанием подзадачи
   - Указать в плане информацию о созданных подзадачах

5. **Запросить недостающую информацию**:
   - Если в процессе анализа возникли вопросы
   - Если требуется уточнение требований
   - Если не хватает информации для оценки

### Шаг 4: Согласование плана

1. **Запросить подтверждение** у пользователя
2. **Дождаться ответа**:
   - Если пользователь согласен → перейти к Шагу 5
   - Если есть корректировки → внести изменения в `task.draft.md` и повторить согласование
   - Если есть вопросы от пользователя → ответить и уточнить план

### Шаг 5: Финализация плана

После согласования:
1. **Заменить task.md** содержимым `task.draft.md`
2. **Удалить task.draft.md**
3. **Закоммитить план**:
   ```bash
   git add .agent_tasks/todo/task-name/
   git commit -m "docs(tasks): добавить план для задачи task-name

   🤖 Generated with [Claude Code](https://claude.com/claude-code)

   Co-Authored-By: Claude <noreply@anthropic.com>"
   ```
4. **Сообщить пользователю** что задача готова к выполнению

### Шаг 6: Информирование о следующем шаге

После финализации плана сообщить пользователю:

```
✅ Задача проанализирована и готова к выполнению!

📋 Следующий шаг: Выполнить задачу используя команду:
   /do-process-task task-name

Или просто:
   /do-process-task
```

## Примеры использования

```bash
# Проанализировать конкретную задачу
/do-analize-task task-name

# Показать список доступных задач
/do-analize-task list

# Проанализировать следующую задачу (первую по алфавиту)
/do-analize-task
```

## Проверки безопасности

Перед анализом любой задачи:
- ✅ Работа на feature branch (НЕ на main/master)
- ✅ Контекст проекта загружен (`/load-context`)
- ✅ Требования задачи полностью понятны
- ✅ Если что-то неясно - запросить уточнение у пользователя

Перед финализацией плана:
- ✅ План согласован с пользователем
- ✅ Все вопросы и риски документированы
- ✅ Оценка времени выполнения реалистична
- ✅ Критерии готовности четкие и измеримые
- ✅ Если задача > 5 часов - созданы подзадачи

## Работа со сложными задачами

### Когда создавать подзадачи

Создавать подзадачи если:
- Общая оценка времени > 3-5 человеко-часов
- Задача затрагивает несколько независимых компонентов
- Можно выделить логически независимые этапы
- Пользователь явно запросил разбиение

### Правила создания подзадач

1. **Длительность**: Каждая подзадача не более 3-5 часов
2. **Независимость**: По возможности подзадачи должны быть независимыми
3. **Последовательность**: Если есть зависимости - нумеровать в правильном порядке
4. **Полнота**: Каждая подзадача должна иметь полное описание и критерии готовности
5. **Метаданные**: Указывать зависимости и предусловия если они есть

### Пример разбиения на подзадачи

Исходная задача: "Добавить систему аутентификации" (оценка: 8 часов)

Разбивка:
```
add-authentication/
├── task.md              # Общее описание и план
├── 1-subtask-database/  # Подзадача 1 (2 часа)
│   └── task.md          # Создание схемы БД и миграций
├── 2-subtask-api/       # Подзадача 2 (3 часа)
│   └── task.md          # API endpoints для auth
├── 3-subtask-middleware/# Подзадача 3 (2 часа)
│   └── task.md          # Middleware для защиты routes
└── 4-subtask-tests/     # Подзадача 4 (1 час)
    └── task.md          # Тесты для auth системы
```

## Особенности workflow

### task.draft.md vs task.md

- **task.draft.md**:
  - Создается агентом для планирования
  - Содержит детальный план с оценками времени
  - Согласуется с пользователем
  - НЕ коммитится в git
  - Удаляется после согласования и переноса в task.md

- **task.md**:
  - Финальное описание задачи
  - Содержит то, что нужно сделать (после согласования)
  - Может содержать результаты выполнения
  - Коммитится в git
  - Переносится в `.agent_tasks/done/` после завершения

### Дополнительные материалы

Задача может содержать дополнительные материалы:
- Диаграммы
- Примеры кода
- Схемы БД
- API спецификации
- Скриншоты

Все материалы хранятся в директории задачи (или в поддиректориях типа `materials/`, `schemas/`, etc.)
